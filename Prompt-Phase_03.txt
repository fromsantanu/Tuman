# Phase 03 — Authentication and Authorization

This phase establishes the security foundation upon which the Administrator, Teacher and Student modules will be built.

**Do not implement the complete Administrator, Teacher or Student business modules yet.**

# 2. CURRENT DATABASE CONTEXT

Phase 02 has already established the following important database design.

The main authentication table is:

```text
tmn_users
```

It contains, among other fields:

* `id`
* `username`
* `password_hash`
* `role`
* `status`
* `created_at`
* `updated_at`
* `last_login_at`

The supported roles are:

```text
ADMINISTRATOR
TEACHER
STUDENT
```

The supported account states include:

```text
ACTIVE
INACTIVE
```

Use the actual values defined in `database/schema.sql`.

Do not create a second user/authentication table.

Do not redesign the existing authentication database unnecessarily.

# 3. PHASE 03 OBJECTIVE

At the end of this phase, Tuman should have a working authentication foundation capable of:

* Login
* Logout
* Password verification
* Session management
* Authentication guards
* Role-based authorization
* Protected pages
* Inactive-account rejection
* Session regeneration
* CSRF protection for state-changing forms
* Safe authentication error handling
* Last-login recording where appropriate

The system must be ready for later Administrator, Teacher and Student modules to build upon.

# 4. LOGIN

Implement the Tuman login functionality.

The login form should accept:

```text
Username
Password
```

The login process should:

1. Validate that required fields are present.
2. Look up the user safely using PDO.
3. Verify the password using `password_verify()`.
4. Check that the account is active.
5. Regenerate the session ID after successful authentication.
6. Store the minimum necessary authenticated identity information in the session.
7. Record `last_login_at` where appropriate.
8. Redirect the user according to role.

Do not store the plaintext password in the session.

Do not log the plaintext password.

Do not expose password hashes to the browser.

---

# 5. PASSWORD HANDLING

Passwords must be handled using PHP's password hashing API.

Use:

```php
password_hash()
password_verify()
```

Do not implement your own password hashing algorithm.

Do not use:

```text
MD5
SHA1
plain SHA256
plaintext passwords
```

for password storage.

If password creation/reset functionality is required to support the authentication foundation, use `password_hash()`.

Do not create an elaborate password-management module yet.

---

# 6. SESSION DESIGN

Implement secure PHP session handling.

After successful login:

```text
Session ID
    ↓
regenerate
    ↓
authenticated session
```

At minimum, store:

```text
authenticated user ID
authenticated role
```

or the smallest equivalent information required by the application.

Do not store unnecessary user information in the session.

Where appropriate, configure secure session cookie properties according to the environment, including:

* HttpOnly
* SameSite
* Secure when HTTPS is actually being used

Do not enable settings that would make local HTTP development impossible without documenting the requirement.

---

# 7. SESSION FIXATION PROTECTION

The session identifier must be regenerated after successful authentication.

Use the appropriate PHP session mechanism.

Verify that an attacker cannot simply retain a pre-login session identifier and continue using it after another user logs in.

Document this security decision.

---

# 8. LOGOUT

Implement logout.

Logout must:

1. Clear authentication state.
2. Destroy the session appropriately.
3. Prevent the previous authenticated session from continuing to grant access.
4. Redirect the user to a safe public page such as the login page or home page.

Do not merely unset one session variable and consider the user fully logged out.

---

# 9. AUTHENTICATION GUARD

Create a reusable authentication guard/helper.

The purpose is to allow later protected pages to say conceptually:

```text
Require authenticated user
```

without duplicating authentication logic on every page.

The guard should:

* Check whether the user is authenticated.
* Redirect unauthenticated users appropriately.
* Avoid exposing sensitive information.

The exact file/class/function design should follow the architecture already established in Phase 01.

Do not introduce a large framework.

---

# 10. ROLE GUARDS

Create reusable role authorization functionality.

Later modules will need functionality conceptually equivalent to:

```text
Require Administrator
Require Teacher
Require Student
```

The role guard must be enforced server-side.

For example:

```text
/admin/...     → Administrator only
/teacher/...   → Teacher only
/student/...   → Student only
```

But the directory structure alone is NOT a security mechanism.

A Teacher who manually enters an Administrator URL must be rejected.

A Student who manually enters a Teacher URL must be rejected.

An Administrator should not automatically be assumed to have every future Teacher/Student operation unless the application's permission model explicitly says so.

Document the initial role policy.

---

# 11. ROLE REDIRECTION

After successful login:

```text
ADMINISTRATOR → Administrator dashboard area
TEACHER       → Teacher dashboard area
STUDENT       → Student dashboard area
```

However, at this phase the actual role dashboards do not need to be fully implemented.

If necessary, create simple placeholder protected pages such as:

```text
/admin/index.php
/teacher/index.php
/student/index.php
```

that demonstrate successful authorization.

These are **authentication/authorization test pages**, not the final business dashboards.

Clearly identify them as placeholders.

---

# 12. INACTIVE USERS

An inactive user must not be allowed to authenticate.

For example:

```text
Username exists
Password is correct
Status = INACTIVE
```

must still result in login rejection.

Use a generic and safe login error.

Do not reveal unnecessary information such as:

```text
"This username exists but has been deactivated."
```

unless there is a deliberate product reason to expose that distinction.

Prefer a message that does not help an attacker enumerate accounts.

---

# 13. USER ENUMERATION

Do not reveal whether a username exists through noticeably different authentication messages.

For example, avoid separate public messages such as:

```text
Username does not exist.
Password is incorrect.
```

Prefer a generic authentication failure message.

Be careful not to introduce unnecessary timing differences through obviously different processing paths.

Do not over-engineer this, but follow normal authentication security practices.

---

# 14. CSRF PROTECTION

Implement a reusable CSRF protection mechanism for state-changing forms.

At minimum, it should support:

* Generating a token
* Storing it securely in the session
* Including it in relevant forms
* Validating it on submission
* Rejecting invalid or missing tokens

State-changing operations include, for example:

```text
POST
PUT
PATCH
DELETE
```

as applicable to the current application architecture.

The login form may be protected by CSRF as well if appropriate to the implementation.

Do not create a token system that is difficult for later modules to reuse.

Document how later developers should use the CSRF helper.

---

# 15. INPUT VALIDATION

Validate login input server-side.

At minimum:

* Username is present.
* Username is within reasonable length limits.
* Password is present.

Do not unnecessarily impose restrictive username rules that conflict with the existing database design.

Use safe parameterized queries.

---

# 16. DATABASE ACCESS

Continue using the existing PDO architecture from Phase 02.

Do not introduce another database connection mechanism.

Do not concatenate user input into SQL.

For example, do not build SQL like:

```text
SELECT ... WHERE username = '$username'
```

Use parameterized queries.

Follow the database error-handling approach already established in Phase 02.

---

# 17. LAST LOGIN

Where supported by the existing schema, update:

```text
last_login_at
```

only after successful authentication.

Do not update it for failed attempts.

Use a safe and consistent timestamp strategy matching the existing application/database timezone policy.

Do not introduce an inconsistent timezone convention.

---

# 18. AUTHENTICATION ERROR HANDLING

Authentication failures should:

* Be safe
* Be understandable
* Not reveal sensitive information
* Not expose SQL/database errors
* Not expose PHP warnings or stack traces

For example:

```text
Invalid username or password.
```

is preferable to exposing internal database information.

Development logs may contain technical information where appropriate, but never log plaintext passwords.

---

# 19. AUTHENTICATED PAGE ACCESS

Create a reusable mechanism for protecting pages.

Test at least these cases:

```text
Not logged in → /admin/...     → rejected
Not logged in → /teacher/...   → rejected
Not logged in → /student/...   → rejected
```

and:

```text
Administrator → admin area     → allowed
Teacher       → teacher area   → allowed
Student       → student area   → allowed
```

Cross-role access must be rejected.

---

# 20. AUTHORIZATION MUST BE SERVER-SIDE

This is a fundamental Tuman rule.

Do not consider the following sufficient:

```text
Hide Admin menu from Teacher
```

The server must still reject:

```text
Teacher → manually enter Admin URL
```

Likewise:

```text
Student → manually enter Teacher URL
```

must be rejected.

Later Teacher/Student ownership checks will build on this authorization layer.

---

Phase 03 establishes role authorization.

Do NOT yet implement complete teacher-student ownership logic.

However, design the authorization helpers so later phases can enforce rules such as:

```text

Student   → only own records
```

The database already contains:

```text
tmn_teacher_students
```

and later business modules will use it.

Do not duplicate ownership logic throughout the application.

# 33. IMPORTANT SECURITY RULE

Never trust:

```text
$_GET
$_POST
$_REQUEST
cookies
hidden form fields
URL parameters
```

to determine the user's identity or permissions.

The authenticated identity must come from the secure server-side session.

Role authorization must be based on trusted server-side authentication state.

Later ownership authorization must use database relationships and server-side checks.

* Invoice calculations
* Attendance calculations
* Billing rules
* Payment calculations
* Teacher-student business logic

Keep the authentication layer focused.
